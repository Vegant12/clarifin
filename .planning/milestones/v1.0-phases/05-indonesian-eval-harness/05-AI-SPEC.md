## 1. System Classification

**System Type:** Extraction

**Description:**
A developer-runnable offline eval harness that uploads IDX-listed company financial PDFs to the Gemini Files API, prompts Gemini to extract structured numeric facts (revenue, net income, total assets, total equity, operating cash flow) plus citation page numbers, then scores the results against hand-curated ground truth JSON fixtures. Used by the solo developer to gate Phase 6 (AI Explanation feature) — `pnpm eval` must exit 0 across all 9 documents before the explanation layer is considered production-ready. "Good" means extracted numeric values fall within ±0.5% of audited figures for digital PDFs, ±2% for scanned, and cited page numbers match the actual location of the fact in the PDF.

**Critical Failure Modes:**
1. Numeric extraction drift — Gemini returns a figure that is off by >0.5% on a non-scanned document (e.g., reads consolidated revenue instead of parent-only, or uses prior year instead of latest year)
2. Citation page hallucination — Gemini cites a page number that does not contain the claimed fact, making the citation gate meaningless
3. Indonesian vocabulary misparse — Gemini mis-translates a Bahasa Indonesia label (e.g., confuses "laba bersih" net profit with "laba kotor" gross profit) and maps the value to the wrong key
4. Scanned-PDF OCR failure — Gemini's native vision returns garbled or missing numeric content from an image-only page, causing all numeric assertions to fail for that document
5. Threshold gate decorative — a broken prompt still scores ≥90% because the test tolerances are too wide or the broken-prompt path is not actually wired to a different extraction behavior

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Indonesian equity markets / IDX financial reporting (retail investor tooling)

**User Population:** Two layers: (1) the solo developer who runs `pnpm eval` as a quality gate before shipping; (2) downstream, the urban Indonesian retail investor who receives AI-generated explanations derived from the extracted figures. The retail investor cannot read financial statements and trusts the AI output to inform real investment decisions.

**Stakes Level:** High

**Output Consequence:** Extracted numeric figures (revenue, net income, total assets) become the inputs to the AI explanation and holistic score shown to retail investors. If an extraction is wrong — wrong year, wrong consolidation scope, wrong scale — the investor sees misleading figures and may make a materially incorrect buy, hold, or sell judgment on an IDX-listed stock. The eval harness exists precisely to catch extraction errors before they reach the investor.

### What Domain Experts Evaluate Against

---

**Dimension:** Audited-figure accuracy — correct line item, correct year
Good (analyst accepts): Extracted `revenue_latest_year` matches the top-line revenue figure in the audited consolidated income statement for the most recent reporting period, within ±0.5% rounding tolerance.
Bad (analyst flags): Extracted value is the prior-year comparison column (e.g., 2022 figure in a 2023 annual report) or is the unaudited quarterly run-rate rather than the full-year audited figure.
Stakes: Critical
Source: Standard financial analysis practice — analysts always verify the reporting period and audit status before using a figure. IDX annual reports present current-year and prior-year columns side by side; column confusion is a known extraction risk (production RAG research, Daloopa 2024).

---

**Dimension:** Consolidation scope — group figures, not parent-only
Good (analyst accepts): Extracted figures are from the "Laporan Keuangan Konsolidasian" (consolidated financial statements), which combine the parent and all subsidiaries into a single economic entity view — the figure an investor would use to assess the group.
Bad (analyst flags): Extracted figures are from "Laporan Keuangan Entitas Induk" (parent-entity-only statements), which IDX filings present alongside the consolidated statements. For a conglomerate like ASII or INDF, the parent-only revenue can be a small fraction of group revenue.
Stakes: Critical
Source: PSAK 65 (consolidated financial statements, converged with IFRS 10) requires IDX-listed parent companies to present both consolidated and parent-only statements. The two sets appear in the same PDF; the consolidated set is the investor-relevant one. Misidentifying the scope produces materially wrong numbers.

---

**Dimension:** Rupiah denomination and scale — correct currency and unit multiplier
Good (analyst accepts): Extracted numeric value reflects the correct denomination stated in the notes, typically "jutaan Rupiah" (millions of IDR) or "miliaran Rupiah" (billions of IDR), and the extraction keys record the raw figure in the stated unit without scale conversion.
Bad (analyst flags): Extraction treats a figure stated "dalam jutaan Rupiah" (in millions of Rupiah) as raw IDR, understating the actual figure by a factor of one million. Alternatively, extraction silently applies a conversion (e.g., reports in billions when the fixture expects millions) producing a systematic 1,000x error.
Stakes: Critical
Source: All IDX filings include a note stating the denomination unit, typically on the cover or in Note 1. The unit is not always the same across filers — large-cap banks (BBCA) typically report in billions; mid-cap manufacturers may report in millions. An analyst always reads this note before recording any figure.

---

**Dimension:** Bahasa Indonesia label disambiguation — net income vs. gross profit vs. operating income
Good (analyst accepts): `net_income_latest_year` maps to "laba bersih" (profit after tax attributable to owners of the parent), not "laba kotor" (gross profit) or "laba usaha" / "laba operasi" (operating income/EBIT) or "laba sebelum pajak" (pre-tax income).
Bad (analyst flags): Extraction returns the pre-tax figure because the prompt did not distinguish "laba bersih" from "laba sebelum pajak," or returns gross profit because the model associated "laba" with the first occurrence rather than the bottom-line figure.
Stakes: Critical
Source: PSAK income statement structure; practitioner knowledge that Indonesian financial vocabulary has multiple "laba" variants that correspond to materially different subtotals. This is the single biggest Indonesian-language vocabulary risk identified in the project's CLAUDE.md eval harness section.

---

**Dimension:** Citation page accuracy — cited page contains the claimed fact
Good (analyst accepts): The cited page number (PDF page index) is a page where the audited income statement or balance sheet table visibly appears, and the specific figure can be found on that page by a human reviewer.
Bad (analyst flags): The cited page is the cover page, the auditor's report, or a narrative page that discusses the figure in text but does not present the primary tabular statement. Or the citation is off by more than one page from where the table actually starts.
Stakes: High
Source: Clarifin's non-negotiable product constraint: "Every AI-generated factual claim must trace back to a specific page in the source PDF." A citation pointing to the wrong page makes the trust mechanism meaningless — a user who follows the citation and cannot find the number loses confidence in the entire product.

### Known Failure Modes in This Domain

1. **Period column confusion.** IDX income statements and balance sheets present current-year and prior-year figures in adjacent columns. Without explicit column-selection instruction, an LLM following vector similarity may extract the prior-year comparison figure — a real, plausible number that is simply for the wrong year. This failure is silent: the extracted value passes format validation but is factually stale. (Source: production RAG research showing that "Q3 2024 revenue" and "Q3 2023 revenue" occupy nearly the same vector space.)

2. **Consolidated vs. parent-only scope swap.** IDX annual reports include both a "Laporan Keuangan Konsolidasian" and a "Laporan Keuangan Entitas Induk" in the same PDF. For large conglomerates (ASII, INDF, GOTO), the parent-only revenue may be 5–20% of group revenue. An extraction that picks up the parent-only table produces a number that is internally consistent and passes numeric format checks but is categorically wrong for investor use.

3. **Denomination scale misread.** Indonesian filings state denomination units in the header of financial statement tables (e.g., "Dinyatakan dalam jutaan Rupiah / Stated in millions of Rupiah"). If the model reads the number without applying the stated unit, the extracted figure is off by 6 orders of magnitude. This error is detectable by comparison to market-cap order-of-magnitude expectations, but only if the fixture ground truth is denominated consistently.

4. **Segment revenue substitution in conglomerates.** Companies like ASII (Astra International) publish segment revenue breakdowns (automotive, financial services, agribusiness) alongside total group revenue. An extraction prompted for "total revenue" may latch onto a segment subtotal — plausible in magnitude, but not the group-level figure analysts use for valuation.

5. **Bahasa Indonesia label misparse at the "laba" family.** The income statement presents "laba kotor" (gross profit), "laba usaha" (operating profit), "laba sebelum pajak" (pre-tax profit), and "laba bersih" (net profit) as successive subtotals. Without tight label matching, the model may return a higher subtotal — overstating profitability — or a lower one if the document uses variant phrasing like "laba komprehensif" (total comprehensive income, which includes OCI items not in net income).

### Regulatory / Compliance Context

**OJK (Otoritas Jasa Keuangan) — mandatory audited filings:**
All IDX-listed companies must file audited annual financial statements with OJK and IDX within three months of the financial year end, audited by an accountant registered with OJK. Quarterly and mid-year reports may be unaudited or limited-review. The eval harness uses annual reports and audited quarterly filings; ground truth values must be taken from the audited figures, not unaudited interim estimates.

**PSAK (Pernyataan Standar Akuntansi Keuangan) — Indonesian GAAP, IFRS-convergent:**
Indonesian listed companies apply PSAK, which converges with IFRS on a phased basis (typically 1–2 years behind IFRS adoption). Key standards relevant to extraction: PSAK 1 (presentation of financial statements), PSAK 65 (consolidated financial statements, converged with IFRS 10). Consolidated statements are mandatory for parent companies with subsidiaries. PSAK figures are presented in IDR; there is no requirement to present USD equivalents (unlike some markets).

**Disclaimer and non-advice requirement:**
The Clarifin product must label all AI output as "analysis and explanation," not investment advice, and must not make buy/sell recommendations. This constraint is upstream of the eval harness but directly affects how extracted figures are surfaced: accurate extraction is required to make the explanation layer trustworthy enough that users understand they are reading facts from the document, not AI-generated financial advice.

**No direct personal-data regulation applies to this eval harness:**
The harness processes publicly filed IDX documents (not user personal data) and runs offline as a developer tool. PDPA Indonesia (Undang-Undang Perlindungan Data Pribadi, effective 2024) does not apply to public corporate filings.

## 2. Framework Decision

**Selected Framework:** Direct `@google/genai` SDK — no meta-framework

**Version:** `@google/genai` v1.52.x (already in package.json)

**Rationale:**
The harness code is already complete and uses direct Gemini Files API calls via `@google/genai`. The extraction pipeline is single-pass and linear: upload PDF → poll until ACTIVE → send extraction prompt → parse JSON response → score against ground truth. Every meta-framework option (LangChain, LlamaIndex, Google ADK) would add abstraction overhead, introduce Python dependencies or TypeScript-incompatible runtimes, and provide zero capability beyond what the direct SDK already offers. The anti-pattern "use LangChain for simple chatbots — direct SDK call is less code, faster, easier to debug" applies exactly here. Solo dev, TypeScript-only, free-tier budget: the direct SDK is unambiguously correct.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Google ADK | Python-only; TypeScript is a hard constraint for this Next.js project |
| LlamaIndex (TS) | RAG-optimized; adds document-ingestion abstraction that is not needed for a single-pass Gemini Files API call |
| Vercel AI SDK (structured output layer) | Already used in the app layer but not needed in the offline eval runner — direct `@google/genai` is already wired |
| LangChain (TS) | Abstraction overhead with no benefit; extraction pipeline is too simple to justify the dependency |

**Vendor Lock-In Accepted:** Yes (Partial) — Gemini vendor lock-in is already accepted at the project level (see CLAUDE.md stack decision). The eval harness is an internal developer tool, not user-facing; migrating to a different model provider would require rewriting the extraction prompts regardless of framework.

## 3. Framework Quick Reference

> Distilled from existing codebase (`src/lib/eval/`) and `@google/genai` v1.52 docs.

### Installation
```bash
pnpm add @google/genai   # already in package.json — @^1.52.0
```

### Core Imports
```typescript
import { createPartFromUri, GoogleGenAI } from "@google/genai";
```

### Entry Point Pattern
```typescript
// Full PDF upload → poll → extract cycle (mirrors gemini-eval-extract.ts)
const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY });

// 1. Upload PDF bytes
const uploaded = await ai.files.upload({
  file: new Blob([pdfBytes], { type: "application/pdf" }),
  config: { mimeType: "application/pdf", displayName: "BBCA-AR-2023.pdf" },
});

// 2. Poll until ACTIVE (state machine: PROCESSING → ACTIVE | FAILED)
let file = await ai.files.get({ name: uploaded.name! });
while (file.state === "PROCESSING") {
  await new Promise((r) => setTimeout(r, 1500));
  file = await ai.files.get({ name: uploaded.name! });
}
if (file.state === "FAILED") throw new Error("Gemini file processing failed");

// 3. Send PDF part + extraction prompt in one generate call
const response = await ai.models.generateContent({
  model: "gemini-2.5-flash",
  contents: [
    createPartFromUri(file.uri!, file.mimeType ?? "application/pdf"),
    { text: PROMPT_EVAL_BASE },
  ],
});

// 4. Parse JSON response (no markdown fences — prompt enforces plain JSON)
const extraction = JSON.parse(response.text!);

// 5. Best-effort cleanup (48h TTL anyway — delete to stay within storage quota)
await ai.files.delete({ name: uploaded.name! }).catch(() => {});
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `ai.files.upload()` | Uploads a binary blob to Gemini Files storage; returns a `name` handle | Before every extraction run; PDF must be uploaded each time (no persistent caching between harness runs) |
| `ai.files.get({ name })` | Fetches file metadata including `state` (`PROCESSING` \| `ACTIVE` \| `FAILED`) | Poll in a loop after upload until state is `ACTIVE` before calling `generateContent` |
| `createPartFromUri(uri, mimeType)` | Creates a multimodal content part from a Files API URI | Must be the first element in `contents`; tells Gemini to read the PDF natively |
| `ai.models.generateContent()` | Single-turn generation — sends the PDF part + prompt and returns one response | Used for extraction (not streaming — we need the full JSON before scoring) |
| `response.text` | The raw text of the model's reply | Parse as JSON; if the model wraps in markdown fences, strip them before parsing |

### Common Pitfalls

1. **Calling `generateContent` before file is `ACTIVE`** — upload is async and processing takes 1–10 seconds depending on PDF size; skipping the polling loop causes a "file not found" or "file not ready" error.
2. **Markdown-wrapped JSON response** — even with "reply with ONLY valid JSON (no markdown fences)" in the prompt, `gemini-2.5-flash` occasionally wraps output in ` ```json ... ``` `; always strip ` ```json ` / ` ``` ` before `JSON.parse()`.
3. **Files API 48-hour TTL** — uploaded files are auto-deleted by Gemini after 48 hours; the harness uploads fresh each run, so this is fine, but do not design a cache that assumes persistence beyond 48h.
4. **Free-tier rate limits** — 10 RPM, 250 RPD on Gemini 2.5 Flash free tier; running all 9 documents sequentially takes ~90s and stays well within limits. Do NOT parallelize uploads without rate-limiting — 9 concurrent calls would violate RPM.
5. **`clonePdfBytes()` before converting to `Blob`** — the existing code clones the `Uint8Array` before wrapping in `ArrayBuffer`/`Blob` to prevent `detached ArrayBuffer` errors; omit this and Node.js may throw when the buffer is GC'd mid-upload.

## 4. Implementation Guidance

**Model Configuration:**
- Model: `gemini-2.5-flash` (defined as `EVAL_MODEL_ID` in `src/lib/eval/prompts.ts`)
- Temperature: default (not set) — extraction tasks benefit from greedy/deterministic decoding; `gemini-2.5-flash` defaults to 1.0 but extraction prompts with strict JSON format are robust to this
- Thinking budget: not configured — Flash's default thinking is sufficient; avoid `thinkingConfig: { thinkingBudget: 0 }` as it degrades instruction-following on structured output tasks
- Max output tokens: not set explicitly — JSON extraction of 5 numeric keys + 5 citation facts is well under 1K tokens; the model will not hit limits

**Core Pattern:**
Single-pass extraction — the full PDF is uploaded once, the extraction prompt requests all numeric keys and citation facts in a single `generateContent` call, and the response is validated against the `extractionResultSchema` Zod schema. There is no chunking, no RAG retrieval, and no multi-turn conversation. The 1M token context window of `gemini-2.5-flash` means even the longest IDX annual report (200+ pages) fits in one call.

**Tool Use:**
No function-calling tools are used. The Gemini Files API is the only external integration — PDFs are uploaded as binary blobs, not converted to text. `createPartFromUri` passes the file reference directly to the model; Gemini handles PDF rendering and OCR natively.

**State Management:**
Stateless per run. The eval harness reads `eval/manifest.json` to enumerate documents, loads fixture files from `eval/fixtures/`, reads PDFs from `eval/pdfs/`, and writes results to stdout/process exit code. No database writes during eval. The only persistent state is the fixture JSON files themselves (curator-managed, version-controlled).

**Context Window Strategy:**
Full-document approach — do not chunk. The 1M token context window handles the largest IDX annual reports (ASII at 200+ pages ≈ ~50K–100K tokens). Chunking would break citation page accuracy because page numbers must be referenced relative to the full document index. Pass the entire PDF as a single Files API part.

## 4b. AI Systems Best Practices

> TypeScript edition — Zod replaces Pydantic in this stack.

### Structured Outputs with Zod

```typescript
// src/lib/eval/schema.ts — the Zod schema is the contract between Gemini and the harness
import { z } from "zod";

export const extractionResultSchema = z.object({
  numericExtractions: z.array(z.object({
    key: z.string().min(1),
    valueIDR: z.number().finite(),
    sourcePage: z.number().int().positive().optional(),
  })),
  citedFacts: z.array(z.object({
    id: z.string().min(1),
    text: z.string(),
    citedPages: z.array(z.number().int().positive()).min(1),
  })),
});

// Validation in load-manifest.ts:
export function parseEvalExtractionResponse(raw: string): EvalExtraction {
  const stripped = raw.replace(/^```json\s*/i, "").replace(/```\s*$/, "").trim();
  return extractionResultSchema.parse(JSON.parse(stripped));
}
```

The Zod `parse()` call throws a `ZodError` if Gemini's JSON response doesn't match the schema. This is intentional — a schema mismatch means the prompt broke or the model changed behavior; it should surface as a hard harness failure, not a silent wrong extraction.

Retry logic: the eval runner does not retry on `ZodError` because a schema mismatch is a prompt/model issue, not a transient network error. Transient network errors (fetch failures, 503s) should be retried with exponential backoff up to 3 times before failing the document.

### Async-First Design

The Files API polling loop is inherently async — `ai.files.get()` must be called repeatedly until state transitions from `PROCESSING` to `ACTIVE`. The `while` loop with `await setTimeout` is the correct pattern (already in `gemini-eval-extract.ts`).

The common mistake is calling `generateContent` immediately after `upload()` without waiting for `ACTIVE` state — the API will return an error or empty response because the file is still being processed.

Do NOT parallelize the 9 extraction calls — the free-tier RPM limit (10 RPM) means sequential calls with 1.5s polling intervals will finish all 9 documents in ~3–5 minutes without hitting rate limits. A parallel approach would need a rate-limiter queue.

### Prompt Engineering Discipline

The extraction prompt (`PROMPT_EVAL_BASE`) encodes the full output contract: JSON shape, key naming convention, value units (full IDR integers), citation page semantics, and the "omit rather than fabricate" instruction. This is critical for eval validity:

- **Output format instruction first:** "Reply with ONLY valid JSON (no markdown fences)" must appear at the top before the schema — models follow early instructions more reliably than trailing ones.
- **Explicit unit specification:** "valueIDR MUST be full Indonesian Rupiah integer units printed in the audited statements — convert from billions/trillions only when the column header states the denomination explicitly" — prevents the 10^9 scale error.
- **Omit-rather-than-fabricate:** "If unsure about an amount, omit that numeric row rather than fabricating plausible figures" — a missing key scores 0 but is recoverable; a fabricated value undermines the gate.
- **No few-shot examples in the eval prompt** — examples would leak expected output structure to the model; keep the prompt zero-shot for eval integrity.

### Context Window Management

No chunking needed. `gemini-2.5-flash` has a 1M token context window. The full PDF is passed as a Files API binary part (not token-counted the same way as text). The extraction prompt is ~200 tokens; the response is ~500 tokens. There is no risk of hitting context limits for any IDX filing in the 9-document corpus.

For scanned PDFs (image-only pages), Gemini uses vision tokens instead of text tokens. A 100-page scanned PDF may consume ~20K–50K vision tokens — still well within the 1M limit.

### Cost and Latency Budget

| Item | Free Tier Limit | Harness Usage | Headroom |
|------|----------------|---------------|----------|
| Gemini 2.5 Flash RPM | 10 | 1 call/doc × 9 docs = 9 calls (sequential, ~3 min) | Comfortable |
| Gemini 2.5 Flash RPD | 250 | 9 calls/run; ~27 full corpus runs per day | 27× |
| Files API storage | 20 GB | 9 PDFs × ~10 MB avg = ~90 MB per run; deleted after each run | Negligible |
| Files API TTL | 48h | Irrelevant — harness deletes files after extraction | N/A |

Per-run cost on paid tier: ~$0.003–0.01 (9 PDFs × 100–200 pages × $0.30/1M input tokens). Free tier covers all dev/CI usage until significant traffic scales the app.

Caching strategy: do not cache Gemini Files API URIs across runs — the 48h TTL and the harness's best-effort cleanup mean cached URIs may be invalid. Upload fresh each `pnpm eval` invocation.

## 5. Evaluation Strategy

> This is an offline developer eval harness, not a real-time user-facing system. Eval tooling is the harness itself. Dimensions are derived directly from the domain rubric ingredients in Section 1b.

### Dimensions

| Dimension | Pass / Fail Rubric | Measurement Approach | Priority |
|-----------|-------------------|---------------------|----------|
| **Numeric extraction accuracy** | PASS: `withinTolerance(extracted, expected, tolerancePct)` returns true for ≥90% of `numericExpectations` across all 9 documents. Digital PDF tolerance = 0.5%; scanned tolerance = 2.0% (per D-06). FAIL: Any document causes overall `overallNumericPct` to drop below 90%, or any single fixture field differs by more than the per-document `tolerancePct`. | Code — `withinTolerance()` in `score-run.ts`; arithmetic comparison against ground truth `numericExpectations` | Critical |
| **Citation page accuracy** | PASS: For each `citationExpectation`, at least one value in `citedPages` from the extraction appears in the fixture's `allowedPages` set. ≥90% of citation expectations must pass across all 9 documents (`overallCitationPct ≥ 0.90`). FAIL: Gemini cites a page outside `allowedPages` (e.g., cites the cover page or auditor's report rather than the income statement table) for more than 10% of expectations. | Code — set intersection: `citedPages ∩ allowedPages ≠ ∅` in `score-run.ts` | Critical |
| **Indonesian vocabulary fidelity** | PASS: Extracted key names match the snake_case anchors defined in `PROMPT_EVAL_BASE` (`revenue_latest_year`, `net_income_latest_year`, `total_assets_latest_year`, `total_equity_latest_year`, `operating_cash_flow_latest_year`). `net_income_latest_year` value falls within tolerance of the audited "laba bersih" bottom-line figure, not "laba kotor" (gross profit) or "laba sebelum pajak" (pre-tax income). FAIL: Key is absent (model omitted rather than fabricated, which is acceptable), OR key is present but value is materially wrong in a way consistent with a vocabulary confusion — e.g., `net_income` value matches the gross-profit line within 1% while differing from net income by >20%. | Code — key-presence check + numeric tolerance test. Human spot-check (developer opens PDF, confirms which "laba" line the value corresponds to) for any document where net_income tolerance fails but a gross-profit-sized figure was returned. | Critical |
| **Scanned-PDF OCR extraction** | PASS: For the scanned document slot (e.g., BISI.JK or equivalent), numeric and citation accuracy both meet the widened 2.0% tolerance. No `numericExtraction` entry returns `0` or `null` for a field that is visibly present in the audited statements. FAIL: Gemini returns missing or zero values for figures that a human reviewer can see on the image-only pages, indicating native PDF vision failure on the scanned format. | Code — same `withinTolerance()` applied to scanned-slot documents with `tolerancePct: 2.0`. Human verification: developer opens the scanned PDF, confirms Gemini's extracted value is close to the printed number. | High |
| **Broken-prompt gate effectiveness** | PASS: Running `EVAL_PROMPT_VARIANT=broken pnpm eval` (which substitutes `PROMPT_EVAL_BASE` with `PROMPT_EVAL_BROKEN`) causes `overallNumericPct < 0.50` or `overallCitationPct < 0.50` on at least one document, and the harness exits non-zero. FAIL: The broken-prompt run still exits 0 or scores ≥90% on all dimensions — meaning the gate is decorative and would not catch a regressed prompt in production. | Code — process exit code check; compare aggregate scores between baseline run and broken-prompt run. Offline Vitest tests in `score-run.test.ts` also cover this path without a live Gemini call. | Critical |
| **Schema compliance** | PASS: Every document's Gemini response parses successfully through `extractionResultSchema` (Zod), producing a valid `EvalExtraction` object. FAIL: Any document causes a `ZodError` — meaning Gemini returned a response that doesn't match the expected JSON shape (missing required fields, wrong types, or markdown-fenced output that wasn't stripped). | Code — Zod `parse()` in `parseEvalExtractionResponse()`; a ZodError halts the run for that document immediately | Critical |

### Eval Tooling

**Primary Tool:** Custom Vitest + `@google/genai` harness (already built)

No external eval platform (RAGAS, Arize Phoenix, Braintrust, Promptfoo) is required for Phase 5. The harness IS the eval tool: `scripts/eval/run.ts` drives the extract-and-score loop, `src/lib/eval/score-run.ts` computes all metrics, and Vitest covers the offline scoring unit tests. RAGAS and Langfuse belong in Phase 11 (Observability) when the explanation layer needs production tracing — not here.

### Reference Dataset

**Size:** 9 documents (fixed corpus — `eval/manifest.json` is the dataset definition)

**Composition:**

| Slot | Company | Type | Key Risk Covered |
|------|---------|------|-----------------|
| `bbca-ar-2023` | BBCA (Bank Central Asia) | Large-cap bilingual digital annual | Baseline extraction; bilingual EN+ID label handling |
| `bjbr-ar-variant` | BJBR (Bank BJB) or BBCA prior year | Large-cap bilingual digital annual (variant) | Second bilingual format to verify generalization beyond BBCA layout |
| `tlkm-ar-digital-id` | TLKM (Telkom Indonesia) | Mid-cap ID-only digital annual | ID-only label parsing; "laba bersih" family disambiguation |
| `indf-or-smgr-annual` | INDF (Indofood) or SMGR | Mid-cap ID-only digital annual (manufacturing) | Consolidation scope — INDF has significant subsidiaries |
| `small-cap-scanned` | BISI International or equivalent | Small-cap scanned (image-heavy) annual | Scanned-PDF OCR path; widened tolerance validation |
| `smgr-or-goto-quarterly` | SMGR or GOTO quarterly filing | Quarterly filing | Unaudited vs. audited figure discrimination; period column confusion |
| `asii-long-form` | ASII (Astra International) | Long-form annual (200+ pages) | Segment revenue substitution risk; 1M context window validation |
| `ptba-or-adro-mining` | PTBA (Bukit Asam) or ADRO | Mining annual — dense tables | Heavy-table extraction; denomination scale (jutaan vs. miliaran) |
| `goto-quarterly-pack` | GOTO (GoTo) quarterly pack | Quarterly pack | Multi-entity quarterly structure; parent-only vs. consolidated risk |

**Per-document fixture spec (per D-05 and D-07):**
- 3–5 `numericExpectations` per document: `revenue_latest_year`, `net_income_latest_year`, `total_assets_latest_year`, `total_equity_latest_year`, and optionally `operating_cash_flow_latest_year`
- 3–5 `citationExpectations` per document: facts tied to identifiable statement pages (income statement, balance sheet, auditor's report date)
- `tolerancePct`: `0.5` for digital documents, `2.0` for scanned slot

**Labeling approach (per D-04):**
1. LLM-assisted first pass — run `extractEvalClaims()` against the PDF to get Gemini's candidate extraction output
2. Human visual verification — developer opens the PDF in a viewer, locates the audited consolidated income statement and balance sheet, confirms that each candidate value matches the printed figure and is from the correct table (consolidated, not parent-only), correct year, and correct denomination
3. Record verified values in the fixture `numericExpectations` with the audited figure as `expectedValue`
4. Record `allowedPages` by reading the PDF page index (not the printed page number) for each statement table, including ±1 page to cover renderer variance

Ground truth values must be taken from OJK-filed audited statements only (not unaudited interim estimates). All `expectedValue` figures are recorded in the unit stated by the filing's denomination note (millions or billions of IDR as printed — no unit normalization applied by the curator).

## 6. Guardrails

> This is an offline batch developer tool, not a real-time user-facing service. The guardrail framing is recast accordingly: "Online" = per-run blocking gates that halt or fail the current `pnpm eval` invocation; "Offline" = periodic corpus maintenance actions that keep the dataset valid over time.

### Per-Run Blocking Gates (replaces "Online" guardrails)

| Gate | Trigger | Intervention |
|------|---------|--------------|
| **Schema validation failure** | `parseEvalExtractionResponse()` throws `ZodError` for any document's Gemini response | Halt scoring for that document immediately. Log the document name and ZodError message to stdout. Mark document as `status: "schema_error"` in the run report. Continue to next document (do not abort the entire run, so other documents still produce scores). Overall run exits non-zero. |
| **Gemini file processing failure** | `ai.files.get()` returns `state === "FAILED"` after upload | Mark document as `status: "file_failed"`. Log the document name and file name to stderr. Continue to next document. Overall run exits non-zero because a failed document cannot contribute to the ≥90% threshold. |
| **Fixture still placeholder** | `fixture.fixtureStatus === "placeholder"` at load time | Skip extraction entirely for that document. Count it as a failed document in aggregate scoring (placeholder = gate not yet met). Log clearly: `[SKIP] bbca-ar-2023: fixture is placeholder — counted as failure`. Overall run exits non-zero until all 9 fixtures are `"ready"`. |
| **Aggregate threshold not met** | `overallNumericPct < 0.90` OR `overallCitationPct < 0.90` after scoring all documents | Print a structured failure summary showing per-document pass/fail breakdown and the two aggregate percentages. Exit process with code 1. Phase 6 CI must not merge while this gate is open. |
| **Broken-prompt must fail** | `EVAL_PROMPT_VARIANT=broken` is set | If the broken-prompt run exits 0 or scores ≥90% on all dimensions, this is itself a gate failure — it means the scoring tolerances are too permissive to catch a degraded prompt. Documented in `score-run.test.ts` offline tests; also verifiable with a live run. |

### Corpus Maintenance (replaces "Offline" flywheel)

| Trigger | Action |
|---------|--------|
| IDX company files a new annual report (year rollover) | Update the affected fixture's `numericExpectations` and `citationExpectations` to the new year's audited figures. Re-run `pnpm eval` to confirm the gate still passes. Commit updated fixture. |
| New extraction failure pattern discovered post-Phase 6 launch (e.g., a document type not in the 9-document corpus exposes a vocabulary miss) | Add a 10th document to `eval/manifest.json` covering the new failure pattern. Write a fixture. Re-run gate. |
| Gemini model version change (e.g., `gemini-2.5-flash` deprecated, successor released) | Re-run full corpus against the new model ID before updating `EVAL_MODEL_ID` in `prompts.ts`. Accept a re-calibration run to widen tolerances only if the new model is genuinely less precise on scanned PDFs — do not widen tolerances to hide numeric drift on digital documents. |
| `tolerancePct: 0.5` consistently missed on a digital document by a small margin (e.g., 0.6%) | Investigate root cause first (denomination unit mismatch? rounding in the fixture?). Widen tolerance only if the miss is confirmed as a PDF rendering artifact, not a vocabulary or scope error. Document the decision in a fixture comment. |

## 7. Production Monitoring

> The eval harness is a developer tool with no production users. "Production monitoring" for this phase means run-level observability: what did each run produce, did the gate pass, and where did failures occur. There is no live service to monitor, no sampling strategy, and no real-time alerting.

### Tracing Tool

**Primary:** Console output (stdout/stderr) — the `scripts/eval/run.ts` runner prints a structured JSON-compatible report per document and a final aggregate summary. The process exit code (0 = pass, non-zero = fail) is the CI signal consumed by GitHub Actions.

**Langfuse:** Not wired in Phase 5. Langfuse is the chosen observability platform for this project (CLAUDE.md) and will be integrated in Phase 11 (Observability & Reliability) when the production explanation layer is live and run history, prompt versioning, and token cost tracking become relevant. For a 9-document offline harness that runs in ~3–5 minutes and produces a deterministic pass/fail, console output is sufficient.

### Key Metrics

| Metric | Source | Gate Threshold |
|--------|--------|---------------|
| `overallNumericPct` | `aggregateScores().numericPct` — ratio of passing `numericExpectations` across all ready documents | ≥ 0.90 to exit 0 |
| `overallCitationPct` | `aggregateScores().citationPct` — ratio of passing `citationExpectations` across all ready documents | ≥ 0.90 to exit 0 |
| Per-document `numericPassCount / numericTotal` | `scoreDocument()` output for each manifest entry | Logged per document; no per-document gate (aggregate gate is the blocker) |
| Per-document `citationPassCount / citationTotal` | `scoreDocument()` output for each manifest entry | Logged per document |
| `fixtureStatus` count | Number of `"ready"` vs `"placeholder"` fixtures at run start | All 9 must be `"ready"` for the gate to be achievable |
| Total run time | Wall clock from run start to final score output | Informal; expected 3–5 minutes for 9 documents sequential. No hard threshold — informational only. |

### Alert Thresholds

There are no automated alerts (no service, no on-call). The CI exit code is the alert mechanism:

- **Exit 0:** Gate passes. Phase 6 PR may merge.
- **Exit non-zero:** Gate blocked. The run report printed to stdout identifies the specific document(s) and dimension(s) that failed. Developer investigates before re-running.

For run failures caused by API errors (Gemini 503, rate limit exceeded mid-run), the runner logs the error with the document name and exits non-zero. These are transient and can be re-run — they do not indicate an extraction quality problem.

### Smart Sampling Strategy

Not applicable. The corpus is a fixed 9-document set; every document is processed on every run. There is no sampling, no weighting, and no signal-based prioritization — run the full corpus every time to ensure the gate is comprehensive and reproducible.

When the corpus is expanded in a future phase (e.g., Phase 12 eval refresh), sampling considerations may apply if the corpus grows beyond ~30 documents and full-corpus runs begin consuming a meaningful fraction of the 250 RPD free-tier quota.
