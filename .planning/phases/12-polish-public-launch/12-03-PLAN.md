<objective>
Implement per-IP daily upload rate limiting without a separate counter table: count existing `documents` rows for the same IP created in the last 24 hours, and reject with HTTP 429 when the count reaches 5. Store the client IP on every successful documents insert.

CRITICAL NOTE: The `documents` table does NOT have an `ip_address` column yet (confirmed from database.types.ts). This plan adds the column via a Supabase migration as Task 1. The migration must be applied (pnpm supabase db push) before the route changes in Task 2 will typecheck.

Purpose: INFRA-02 — protect free-tier Gemini/Supabase quotas from a single IP hammering uploads. 5 uploads/IP/day is a generous limit for a personal research tool while preventing abuse.

Constraint: Do NOT put rate limiting in Next.js middleware — middleware runs on the Edge runtime which does not support the Supabase admin client (uses Node.js-only APIs). Rate limiting goes directly in the route handler.
</objective>

    Step 2 — Create src/lib/rate-limit.ts:

    ```ts
    import "server-only";

    import { supabaseAdmin } from "@/db/client";

    /** Maximum number of uploads allowed per IP address within a rolling 24-hour window. */
    const DAILY_UPLOAD_LIMIT = 5;

    /**
     * Extracts the client IP address from the request.
     * Vercel sets the x-forwarded-for header; the leftmost IP is the client.
     * Falls back to "unknown" for local development environments.
     */
    export function extractClientIp(request: Request): string {
      const xff = request.headers.get("x-forwarded-for");
      if (xff) return xff.split(",")[0]!.trim();
      return "unknown";
    }

    /**
     * Returns true if the given IP has reached the daily upload limit.
     * Counts documents rows for this IP created within the last 24 hours.
     *
     * Fails OPEN on DB error — if the check cannot be performed, the upload proceeds.
     * This prevents a DB outage from locking out all users.
     */
    export async function isIpRateLimited(ip: string): Promise<boolean> {
      const since = new Date(Date.now() - 24 * 60 * 60 * 1000).toISOString();
      const { count, error } = await supabaseAdmin
        .from("documents")
        .select("id", { count: "exact", head: true })
        .eq("ip_address", ip)
        .gte("created_at", since);

      if (error) {
        // Fail open: do not block the user if we cannot check the rate limit.
        console.error("[rate-limit] DB error checking upload rate:", error.message);
        return false;
      }

      return (count ?? 0) >= DAILY_UPLOAD_LIMIT;
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Internet → upload-init route | x-forwarded-for header is user-controllable on direct connections; Vercel sets it authoritatively in production |
| Rate limit DB query | supabaseAdmin is server-only; the query runs in the route handler, never client-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-03-01 | Spoofing | x-forwarded-for IP extraction | accept | On Vercel, the platform sets x-forwarded-for — end users cannot spoof it. In local dev, "unknown" is used, which means the limit counts all local uploads together. Acceptable for a hobby-tier protection mechanism. |
| T-12-03-02 | Denial of Service | isIpRateLimited fails open | accept | Fail-open is the correct choice for rate limiting availability. A DB outage should not lock out all legitimate users. The risk of a DB outage enabling quota abuse is lower than the risk of blocking all users. |
| T-12-03-03 | Information Disclosure | ip_address stored in documents | mitigate | ip_address column is accessible only via supabaseAdmin (service role key, server-side only). The column is not exposed via any public API or client-side Supabase query. No Supabase RLS policies need updating since documents table has no public reads in v1. |
| T-12-03-04 | Elevation of Privilege | 429 bypass via header manipulation | accept | Hobby-tier rate limit. A determined attacker can use different IPs. This protects against accidental hammering and casual abuse, not adversarial circumvention. |
</threat_model>
