<objective>
[BLOCKING] Migrate `document_analysis.explanation` from `text` to `jsonb` so downstream
plans can upsert a plain JS object via Supabase JS client without manual `JSON.stringify`.
Per RESEARCH.md §"explanation Column: jsonb Migration" and CONTEXT.md D-06, this is the
cleaner path: the column is currently NULL for all rows (no data to convert), `jsonb` is
already used for `score_breakdown` in the same table (consistency), and `jsonb` enables
Phase 7/8 to query individual sections via `explanation->>revenue` without full-string
deserialize.

This plan creates the migration SQL, runs `supabase db push` (requires `SUPABASE_ACCESS_TOKEN`
env var or interactive login — Docker not needed for remote push), and regenerates
`database.types.ts` to reflect the new `Json | null` column type.

The schema push is BLOCKING for Plan 03 and Plan 04. Plan 03's `analyze-document-batch.ts`
upserts `{ explanation: result }` as a plain object — this only works if the column is `jsonb`.
If this plan is not committed and pushed before Plan 03 lands, every Plan 03 upsert will
silently corrupt to `"[object Object]"` (Pitfall 6 from RESEARCH.md).

Purpose: Lock the storage shape (jsonb) so Plan 03 service code stays simple and Plan 04
status route can read sections cleanly.

Output: 1 SQL migration file + regenerated database.types.ts + remote schema updated.
</objective>
